# 自动报工（MCP）

核心逻辑由 **MCP 服务** 提供，本 skill 只描述工具编排与流程。**不包含任何 Python 代码或 BIP 内部配置。**

> ⚠️ 使用前需已连接 MCP 服务：`streamable http` → `http://<MCP服务器>:51889/mcp`（工具名前缀 `bip_`）。
> ⚠️ 所有流程内部已含登录+考勤扫描，不要拆成多步。账号密码从对话获取，作为 `username`/`password` 参数**必传**给每个工具（各用户用自己的 BIP 账号，服务器不提供默认凭据）。

## 可用工具

| 工具 | 说明 |
|---|---|
| `bip_scan` | 扫描最近 30 天考勤，返回待报工/已报工/异常/无考勤 |
| `bip_submitted` | 查询已提交报工单及审批状态（可选按日期/状态/单号筛选） |
| `bip_list_phases` | 查询可选任务/阶段列表（需工作类别；项目类需项目） |
| `bip_form_data` | 生成报工表单数据 JSON（`【表单数据】...【表单数据结束】`包裹） |
| `bip_report` | 单日报工：考勤→匹配任务/项目→提交→审批→更新状态 |
| `bip_auto_report` | 批量自动报工所有待报日期 |
| `bip_split_report` | 拆分报工：单日多任务，一次提交单 DocNo 多明细 |
| `bip_delete_doc` | 删除报工单（审批中自动先撤销再删除；审批通过拒绝删除） |
| `bip_revoke_doc` | 撤销指定单号审批（仅审批中有效） |
| `bip_sync_options` | 同步选项快照（一般无需手动调用） |

## ⚡ 触发规则

当用户提到"报工"/"填报工时"/"提交工时"/"扫描考勤"时，按以下逻辑**立即执行**：

```
用户说"报工"
  ├─ 凭据未就绪（用户未提供过账号密码）
  │     → 发「用户引导」欢迎消息，索取账号密码
  │
  └─ 凭据已就绪
        → 🚀 只做两件事（不要发欢迎消息，不要追问，不要查任务列表）：
          1. 调 bip_scan
          2. 调 bip_submitted
          （⚠️ 两条必须**串行**执行——MCP 服务内部已串行，但 agent 侧也不要并行发起）
        → 汇总输出按「分析输出模板」呈现（**表格，紧凑，禁止大段段落**）
        → 有待报工/考勤异常 → 调 bip_form_data 生成报工表单，渲染给用户确认（见「报工表单」）
        → 无待报工 → 用表格说明全部已报工，不生成表单
```

> ⚠️ 拿到考勤和报工单数据之前，禁止调用 bip_form_data 或追问参数。
> ⚠️ 分析报告展示之前，禁止追问日期、工时、任务、内容等参数。

## 用户引导（仅凭据未就绪时使用）

```text
👋 你好！我可以帮你完成 BIP 工时相关的所有操作：

📝 报工流程：
  1️⃣  提供 BIP 账号和密码
  2️⃣  我会自动拉取考勤和报工单，告诉你哪些日期待报工、哪些已报工
  3️⃣  告诉我工作类别（部门工作 / 项目工时 / 销售支持）、任务/阶段、报工内容
  4️⃣  一键提交+审批，支持单日或批量补报

📋 报工单管理：
  • "查看报工单" — 查看已提交报工单及审批状态
  • "删除报工单 RPTxxx" — 删除指定报工单（审批中自动撤销后删除）
  • "撤销报工单 RPTxxx" — 仅撤销审批，不删除

📊 拆分报工（精细化）：
  • "拆分报工 7月10日" — 将一天工时拆分到不同任务
  • 例如：部门工作 skill开发 月结问题处理 6h + 部门工作 skill开发 系统维护 2h + 部门工作 T02会议 课题讨论 2h(加班)

请先提供你的 BIP 账号和密码～
```

## 意图 → 工具映射

| 用户说 | 调用 | 追问条件 |
|---|---|---|
| 只提供凭据，未提"报工"/"扫描" | `bip_scan` + `bip_submitted`（自动分析） | 缺凭据 |
| "扫描" / "查看考勤" | `bip_scan` + `bip_submitted` | 缺凭据 |
| "报工"（凭据就绪，未指定参数） | 自动分析 → 表格展示 → `bip_form_data` 生成表单 | 缺凭据 |
| "报工" + 部分参数 | 先自动分析展示上下文，再 `bip_report` 提交；任务/项目参数未指定时，用 `bip_list_phases` 列出可选列表并让用户选，**禁止自动选第一条** | 追问缺失必填参数 |
| "批量报工" / "自动报工" | 先自动分析展示待报日期，再 `bip_auto_report` | 缺工作类别或内容 |
| "拆分报工" / "精细化报工" | agent 引导用户列出拆分明细，用 `bip_split_report` 逐条传入 | 缺拆分明细 |
| 自动检测拆分（用户未说关键词，但描述同日多任务+多工时） | 同上，自动进入拆分流程 | — |
| "查询已提交" / "查看报工单" | `bip_submitted`（单独执行） | — |
| "查看任务" / "有哪些任务" | `bip_list_phases`（单独执行） | 缺工作类别时追问；项目类缺项目时追问 |
| "删除报工单" + 单号 | `bip_delete_doc` | 缺单号时追问 |
| "撤销报工单" + 单号 | `bip_revoke_doc` | 缺单号时追问 |

> **边界情况**：`bip_scan` 返回 0 条待报工 → 用表格告知全部已报工，不输出报工表单，可提醒"拆分报工/查看/删除/撤销报工单也可告诉我"。`bip_submitted` 返回空 → 报告中标明"无已提交报工单"。两条中有一条失败 → 展示已有结果 + 报错信息，不中断流程。

## 自动分析流程（核心）

当用户说"报工"且凭据已就绪时，agent **必须先执行此流程**，再根据结果引导用户。以下任一场景触发：用户说"报工"/"填报工时"/"提交工时"、用户首次提供凭据、用户说"扫描考勤"。

```text
Step 1: 调 bip_scan       # 范围：从昨天往前推 30 天，不含当天
Step 2: 调 bip_submitted  # 了解审批状态，判断是否可删除/覆盖
```

### 分析输出模板

汇总两条输出，**必须用 markdown 表格**紧凑呈现（数量为 0 的分类省略该表或用"无"），禁止大段段落/列表文字：

```text
📊 考勤与报工单分析报告

🔴 **待报工（N 天）**
| 日期 | 工时 | 打卡 |
|---|---|---|
| 2026-07-02 | 8h | 09:00 → 18:00 |

🟢 **已报工（M 天）**
| 日期 | 工时 | 单号 | 状态 |
|---|---|---|---|
| 2026-06-30 | 8h | RPT20260701001 | 审批中 |

🟡 **考勤异常（K 天，需手动指定工时）**
| 日期 | 打卡 | 工时 |
|---|---|---|
| 2026-06-28 | 09:30 → 17:00 | 0 |

⚪ **无考勤（L 天）**
| 日期 | 说明 |
|---|---|
| 2026-06-25 | 无打卡记录 |

📋 **报工单概况**：审批通过 X 条 ｜ 审批中 Y 条 ｜ 已驳回 Z 条
```

> 表格列按实际数据增减；某分类无数据时不输出该表。

| 分析结果 | 后续动作 |
|---|---|
| 有待报工日期 | 调 `bip_form_data` 生成表单，渲染给用户确认 |
| 有 2+ 天待报工 | 表单默认覆盖全部待报日；用户要"批量报工"再走 `bip_auto_report` |
| 有考勤异常日期 | 表单中该日 hours 留空由用户手动填 |
| 无待报工 | 用表格说明全部已报工，不输出表单 |
| 有已驳回报工单 | 表格后提醒"你有 X 条已驳回报工单，可删除后重新报工" |

## 报工表单（agent 自渲染）

有待报工日期时，跑完 `bip_scan` + `bip_submitted` 后调 **`bip_form_data`**。其输出形如：

```
【表单数据】{ "date": "...", "hours": "...", "rows": [{"date":"...","std_hours":"8","ovt_hours":"0"}, ...],
"workTypes": ["部门工作","项目工时","销售支持"], "commonTasks": {...}, "recentProjects": [...], "projectTasks": {...},
"recent": {"work_type":"部门工作","phase_id":"...","phase_label":"...","content":"","std_hours":"8","ovt_hours":"0"} }【表单数据结束】
```

agent **解析出 JSON** 后，把 `rows`（默认覆盖全部待报日）渲染成紧凑表格给用户核对/编辑：

| 日期 | 工作类别 | 任务/阶段 | 报工内容 | 标准工时 | 加班工时 |
|---|---|---|---|---|---|
| 2026-07-02 | 部门工作 | skill开发 | （用户填写） | 8 | 0 |

- 工作类别、任务/阶段从 `workTypes` / `commonTasks` / `recentProjects` / `projectTasks` 提供候选；项目类选项目后再选该项目的阶段
- 正常日期工时预填考勤值，异常日期留空由用户填
- `content` 字段由用户填写，提交后**原样使用**，禁止润色、缩写

> 若平台能识别 `【表单数据】` 标记自动渲染表单卡片，则直接使用卡片；否则按上表自渲染。

## 表单提交处理

用户确认表单后，**直接按行提交**，不要重新扫描考勤、不要追问、不要重新展示分析报告：

- **1 行** → 调 `bip_report(date, work_type, phase_id, content, [project_id], [hours])`
- **多行（拆分）** → 调 `bip_split_report(date, items)`，每行一个 item：
  - 部门工作（无项目）：`"部门工作|任务ID|内容|标准工时|加班工时"`（5段）
  - 项目类：`"项目工时|项目ID|任务ID|内容|标准工时|加班工时"`（6段）
- `phase_id` / `project_id` 支持名称关键词模糊匹配；匹配失败时先 `bip_list_phases` 解析成真实 ID 再提交
- 若字段缺失或工具报错（如任务不存在、日期已报工），先向用户报告问题，再重新调 `bip_form_data` 让用户修正，**禁止擅自猜测参数**

## 拆分报工流程

1. Agent 引导用户列出每个拆分项：工作类别、任务/阶段、内容、标准工时、加班工时
2. 用 `bip_split_report` 一次传入全部 items（单 DocNo 多明细，BIP 不允许同天多条独立记录）
3. 工具内部：获取考勤 → 解析阶段 → 单次提交多明细 → 审批+改状态

> ⚠️ 禁止用 JSON/文件方式传拆分数据，统一用 items 数组的管道分隔字符串，格式固定。

## 审批状态码

| 状态码 | 含义 | 可删除 | 可撤销 |
|---|---|---|---|
| 1 | 待提交 | ✅ 直接删 | — |
| 2 | 已撤销 | ✅ 直接删 | — |
| 4 | 审批中 | ✅ 自动撤销后删 | ✅ |
| 8 | 审批通过 | ❌ | ❌ |
| 16 | 反审核 | ✅ 直接删 | — |
| 32 | 已驳回 | ✅ 直接删 | — |

## 任务查询双渠道（部门工作）

部门工作的任务查询和报工匹配均按此优先级：**主渠道** 常用任务（用户已配置/使用过的任务，带预填 CostOrg）→ 匹配不到时**回退**到 全量列表。报工时 `phase_id` 先在主渠道模糊匹配 → 匹配不到则回退全量列表。

## 核心规则

- **凭据就绪后必须先自动分析**：用户说"报工"且凭据已就绪时，必须先 `bip_scan` + `bip_submitted`，禁止跳过此步骤直接追问参数
- **分析报告出来前不问参数**：日期、工时、任务、内容等必须在分析报告展示之后、通过报工表单让用户确认
- **自动检测拆分意图**：用户未说"拆分/精细化"，但描述了同日多个任务+工时（如"7月13日 前端4h + 测试4h"），自动识别为拆分报工。判断依据：① 同一日期 ② ≥2 组不同的「内容+工时」描述 ③ 各组工时之和接近当日考勤总工时
- **绝不替用户猜测参数**：`phase_id`、`project_id`、`content` 等关键参数必须由用户明确指定，禁止自动选取第一条
- **报工内容原样传递**：`content` 必须使用用户原话，禁止润色、缩写、改写或补充
- 不猜测任何字段，接口失败立即停止
- 部门工作 → 无需项目；项目工时/销售支持 → 需项目
- 阶段/任务只选可报工的（部门工作/销售支持按 `isLocked`/`isDeleted` 过滤，项目工时按 `canCheck=Y`）
- 考勤异常（工时=0）→ 报错，要求用户指定 `hours`（除非已显式指定）
- 已报工日期 → 禁止重复提交，报错提示先删除原报工单
- 拆分报工 → 单日多任务用 `bip_split_report` 一次提交，不要逐条独立提交
- 审批通过(8) → 不可删除、不可撤销；已撤销(2) → 无需再次撤销
- `bip_submitted` 默认返回最近一批（约 20 条）；接口不支持翻页。用户质疑"查询不全"时，如实说明此限制
- **任务/项目禁止写死**：未提供 `phase_id` 时用 `bip_list_phases` 动态查询展示给用户选择
